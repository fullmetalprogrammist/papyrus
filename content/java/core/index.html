GC

Общий принцип работы

Поколения объектов

  • Объекты делятся на поколения
    • Молодое поколение - новые объекты (те кого недавно создали) и молодые (те кто уже пережил несколько сборок мусора, но еще не достаточно, чтобы считаться старым).
    • Старое поколение - объекты, которые пережили много сборок мусора.

Области кучи

  • Области кучи
    • Для “молодых”, три области
      • Eden
      • S0, S1 (Survivor)
    • Для “старых” - Old generation / Tenured и пр. названия

Стадии сборки мусора

  • Стадии сборки мусора
    • Minor GC - уборка области молодого поколения.
      • Происходит если в Eden не хватает места для размещения новых объектов.
    • Major GC - уборка области старого поколения.
      • Происходит если в области старого поколения не хватает места для перемещения в нее выживших объектов.
      • Перед минорной сборкой JVM прогнозирует, сколько объектов должно перейти в старшую область. Если по прогнозу оказывается, что места в области для стариков не хватит, запускается не только минорная, но и мажорная уборка. Получается полная уборка.
    • Full GC - уборка обеих областей.
    • Дополнительная инфа
      • Не все сборщики умеют отдельно убирать старшую область, поэтому там обычно в логах видно только минорную и полную сборку.

Общий алгоритм работы уборки

  • Как это все работает
    • Когда создается новый объект, он всегда попадает в Eden область.
    • Как только Eden заполняется (т.е. в ней больше нет места для размещения новых объектов), запускается Minor GC.
    • В результате минорной сборки выжившие объекты перемещаются из Eden в одну из Survivor областей. Eden очищается и новые объекты снова можно в нее размещать.
    • Как только Eden заполняется повторно, то опять происходит минорная сборка. В этот раз анализируется Eden и непустая Survivor. Выжившие из обоих областей перемещаются в соседнюю S, а Eden и “текущая” S очищаются.
    • С каждым таким циклом сборки у выживших объектов растет “возраст” (tenuring). Когда он становится достаточным (15 по умолчанию), то объект перемещается в область под старое поколение. Это называется promotion.
      • Кроме того, если вдруг S переполняется, то наиболее живучие объекты могут переместиться в область под старое поколение раньше, чем достигнут порога возраста.

Пауза, пропускная способность, задержка

  • Пауза (STW, Stop-the-World) - это время, в течение которого приложение “замирает”, чтобы сборщик мусора мог корректно проанализировать объекты в куче. Можно сказать, что в это время приложение простаивает.

  • Пропускная способность (throughput) - показывает долю времени, которое приложение тратит на полезную работу, а не на сборку мусора.

    • Throughput=полезноевремяобщеевремя×100%Throughput = \frac{полезное\ время}{общее\ время} \times 100\%
    • Полезное время = общее время - суммарное время на сборку мусора
    • Например, сервис работал 1 час (3600 сек), на сборку мусора суммарно ушло 2 сек, получается thr=3600−23600×100%=35983600×100%≈99.94%thr = \frac{3600 - 2}{3600} \times 100\% = \frac{3598}{3600} \times 100\% \approx 99.94\%

  • Задержка (latency) - время от прихода запроса до отправки ответа.

  • Как эти параметры взаимосвязаны в контексте GC

    • Короткая пауза означает как правило более частые уборки. Длинная пауза - редкие уборки. Т.е. выбор стоит между “часто по чуть-чуть” или “редко, но надолго”.
    • При этом короткие паузы обычно складываются в более длинный простой, стало быть пропускная способность ниже. А более длинные паузы, за счет того что их меньше, часто дают меньший простой, значит пропускная способность выше.
    • Но длинные паузы, хоть и редкие, сильно увеличивают задержку. Так что запросы, попавшие на момент сборки мусора, могут сильно просесть. Например, если обычно запрос выполняется за 50мс, то попав на длинную паузу gc 500 мс, он уже выполнится за 550мс. Поэтому для минимизации задержки короткие паузы выгоднее.
Пауза в моменте Sum время на уборку Througput Latency Когда хорошо
Короткая Больше 🤢 😊 Когда от системы нужен быстрый ответ в моменте: онлайн-бронирование, оплаты, API, трейдинг, чаты и т.д.
Длинная Меньше 😊 🤢 Когда нужно сделать больше работы, а быстрый ответ не нужен: формирование отчетов, массовая загрузка / трансформация данных, генерация / рассылка документов и т.д.

Строка - это объект, причем иммутабельный

  • Строка - это объект, внутри которого находится массив символов.
    • В массиве в современной джаве лежат байты byte[], а не непосредственно символы.
  • Строки в джаве иммутабельные, поэтому абсолютно любое “изменение” по сути порождает новую строку
String mes = "hello";
mes = mes + " world";  // В mes записалась новая строка "hello world", исходный "hello" не изменился
mes = mes.toUpperCase();  // В up записалась новая строка "HELLO WORLD", а "hello world" не изменилась

Сравнение строк через == и .equals()

  • Поскольку строки это объекты, их надо сравнивать через equals, а не через ==
    • Потому что через == сравнятся ссылки, а через equals - контент
    • Плюс из-за пула строк может возникнуть путаница, поэтому equals - это жбшечка, а == - это рулетка
String a = "Hello";
String b = "Hello";
String c = new String("Hello");
if (a.equals(b))  ✅  // true, тк в обоих переменных слово Hello
if (a == b)       ❌  // тоже true, но лишь из-за механизма стринг пула, а не из-за одинаковых слов
    
if (a == c)           // false - обосрались, тк сравниваются ссылки, а не слова
if (a.equals(c))      // true - все корректно, сравнивается текст

Замена выражений при компиляции

String message = "hello" + " " + "world";

Когда компилятор может понять итоговое значение, как в данном случае, в байткоде окажется готовая строка “hello world” вместо выражения "hello" + " " + "world", т.е. конкатенации в рантайме не будет.

final String world = "world";
String message = "hello" + " " + world;

Здесь тоже вместо "hello" + " " + world будет “hello world” без конкатенации в рантайме, потому что компилятору за счет final + присваивания гарантированно известно значение world при компиляции, значит он может вычислить выражение и заменить его на готовую строку.

String world = "world";
String message = "hello" + " " + world;

А вот тут компилятор не сможет заменить "hello" + " " + world на готовую строку, потому что world это обычная переменная, без final, и компилятор не знает ее значение при компиляции.

String pool

Зачем нужен пул

  • Пул строк хранит ссылки на строки и в некоторых случаях JVM может искать строки в пуле и повторно их использовать. Т.о. экономится память и снижается нагрузка на сборщик мусора.

Какие строки попадают в пул

  • Какие строки попадают в пул
    • В пул попадают все литералы
    • Все строки, на которых явно вызван метод .intern()
String a = "hello world";
String message = someString.intern();

Интернирование, метод .intern()

  • “Интернирование” значит “Проверить, есть ли строка в пуле. Если есть, вернуть ссылку на нее. Если нет, поместить строку в пул и вернуть ссылку”.
    • Этим занимается jvm.
  • При вызове intern() мы явно запускаем интернирование.

Создание строк через new и через литерал

Вопрос - сколько строк создается в этом коде?

String a = new String("Hello");

Ответ: две. Первая строка это литерал “Hello”. Она передается в конструктор new String и получается вторая строка. Ссылка на нее сохраняется в переменную a, а первую строку “Hello” в памяти удерживает пул строк.

  • При использовании new всегда создается новая строка в куче.
  • При использовании литерала проводится интернирование.

Примеры для самоконтроля

// Пример 1
String a = "java";
String b = "java";
String c = new String("java");

a == b;
a == c;
a.equals(c);
// Пример 2
String a = new String("hello");
String b = a.intern();
String c = "hello";

a == c;
b == c;
// Пример 3
final String part = "ja";
String a = part + "va";

String dynamic = args.len > 0 ? "ja" : "ja";
String b = dynamic + "va";

a == "java";
b == "java";

Ответ 1

  • a == b : true, литерал “java” помещается в пул строк, ссылка кладется в а. В b кладется ссылка на эту же строку, потому что опять используется литерал “java”, стало быть сначала проверяется пул, а там “java” уже есть. == сравнивает ссылки. Ссылки равны, поэтому true.
  • a == c : false, потому что new String всегда создает новый объект в куче. Объекты разные, ссылки разные, == дает false.
  • a.equals(c) : true, потому что equals сравнивает текст строк.

Ответ 2

  • a == c : false, потому что new String создает новый объект, ссылки разные, == дает false.
  • b == c : true, в a хранится “hello”. Вызов a.intern() приводит к интернированию “hello” и в b оказывается ссылка на “hello” из пула. В c тоже возвращается ссылка на “hello” из пула. Ссылки одинаковые, == дает true.

Ответ 3

  • a == java : true. В пуле окажется “ja” и “java” (“va” вообще есть только в исходном коде, но после компиляции его нет, потому что “ja” + “va” заменятся на “java”, так что “va” и в пуле тоже не будет). В а будет ссылка на “java”, вместо литерала “java” - ссылка на строку “java”, ссылки одинаковые, == дает true.
  • b == "java" : false. Из-за того что dynamic вычислится в рантайме, то и b вычислится в рантайме через конкатенацию. Поиска в пуле не будет, получится новая строка при конкатенации. “java” возьмет ссылку из пула, ссылка с b разная, == даст false.

.equals() и .hashCode()

equals - это логическое “равно - не равно” для объектов

  • .equals() это метод Object, используется для логического сравнения объектов на “равно - не равно”
    • Допустим, 5 == 5 это очевидно, а как сравнить два объекта Address, в которых много полей? Для этого у Address переопределяем equals и пишем в нем логику сравнения.
  • В Object реализация equals сравнивает ссылки на объекты. А например Integer переопределяет метод и сравнивает значения, лежащие в обертках.
  • Объекты на логическое “равно - не равно” всегда надо сравнивать через equals, иначе могут быть сюрпризы.
    • Например, Integer кэширует маленькие значения (в пределах byte) и два маленьких Integer по 100 могут оказаться равны по ==, а Integer по 200 уже будут не равны по ==, так что объекты - всегда сравнивать по equals надо.

hashCode - это число от содержимого объекта

  • hashCode физически это число int
  • Если мы пишем сами реализацию хэша, то обычно пропускаем через хэш-функцию поля объекта
    • По умолчанию в Object реализация хэша зависит от JVM. Четких алгоритмов не известно, важно только что для одного и того же объекта метод .hashCode() должен возвращать одинаковый хэш
  • Хэш нужен в основном для работы коллекций, основанных на хэш-таблице
    • Хэш по сути это быстрый способ понять, в какой бакет класть значение
  • ✏️ Некоторые способы вычислить хэш
Objects.hash(country, city, street, house, apartment);  // Типично когда надо единый хэш из нескольких полей
Long.hashCode(id);  // Integer.hashCode() и т.д.
somestring.hashCode();

Взаимосвязь equals и hashCode

  • Эти методы тесно связаны. hashCode отдельно обычно не переопределяют, обычно только в паре с equals.
  • ⚠️ Правило - “переопределили equals - должны переопределить hashCode”
    • Почему? Потому что если equals для двух объектов дает true, то их хэши ⚠️ обязаны быть одинаковыми.
      • А почему вообще хэши объектов, которые равны по equals, обязаны быть одинаковыми? Что будет, если хэши будут разными?
        • Причина на самом деле проста. Возьмем например HashSet. В сете по определению не может быть двух одинаковых элементов, т.е. если a equals b, то a и b не могут в сете одновременно лежать. Представим, что хэши у них разные, тогда они окажутся в разных бакетах и тогда при добавлении b сет бы не нашел a. Соответственно, не понял бы что уже такой объект есть и добавил бы b. Вот поэтому хэши у них обязаны быть одинаковыми, чтобы сет по хэшу быстро нашел нужный бакет, а потом по equals бы уже проверил наверняка, есть такой объект или нет.

Правило комбинаций полей

  • ✅ Используем одинаковый набор полей в обоих методах. Идеальный вариант.
equals:    фамилия + имя + отчество;
hashCode:  фамилия + имя + отчество;
  • ❌ В hashCode больше полей, чем в equals. Запрещено.
equals:    фамилия + имя;
hashCode:  фамилия + имя + отчество;

Почему? Потому что Петров Эдуард Иванович и Петров Эдуард Валентинович по equals равны (оба они Петров Эдуард), а хэши получаются разные (из-за отчества). Нарушается правило “объекты равны, значит дб одинаковый хэш”

  • 🤔 В equals больше полей, чем в hashCode. Сомнительно, лучше так не делать.
equals:    фамилия + имя + отчество;
hashCode:  фамилия + имя;

Правило “объекты равны, значит дб одинаковый хэш” не нарушается, но получается больше коллизий, поэтому страдает производительность коллекций, основанных на хэш-таблицах. Например, Петров Эдуард Иванович, Петров Эдуард Валентинович, Петров Эдуард Семенович и все прочие Петровы Эдуарды попадут в один и тот же бакет. Стало быть будет больше линейного перебора при поиске объектов.

Как писать equals и hashCode? Какие поля выбрать для сравнения?

  • Базово сначала проверяется равенство ссылок, потом наследство и если это совпадает, тогда уже сравнение по полям.
  • Выбираются поля, которые задают идентичность объекта:
class Address {
    String country;
    String city;
    String street;
    int house;
    int apartment;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;  // <-- Базово проверяем на равенство ссылок
        if (!(o instanceof Address other)) return false;  // <-- и на наследство

        return house == other.house  // <-- Потом уже сравниваем поля
            && apartment == other.apartment
            && Objects.equals(country, other.country)
            && Objects.equals(city, other.city)
            && Objects.equals(street, other.street);
    }

    @Override
    public int hashCode() {  // <-- хэш считаем по полям, которые использовали в equals
        return Objects.hash(country, city, street, house, apartment);
    }
}
  • Если у объекта есть какой-то идентификатор, id например, который и так однозначно его идентифицирует, то можно писать equals только по нему:
class Person {
    long id;  // <-- Есть какой-то id'шник, поэтому можно только по нему сравнивать
    String name;
    int age;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Person person)) return false;
        return id == person.id;
    }

    @Override
    public int hashCode() {
        return Long.hashCode(id);
    }
}

Дополнительные советы

  • После помещения объекта в сет или в ключ мапы, основанные на хэш-таблицах, нельзя менять поля, которые участвуют в расчете хэша, т.к. хэш изменится и не удастся найти эти объекты.
  • В lombok есть аннотации, упрощающие реализацию equals и hashCode. Просто влепить по всем полям наверное не стоит, но там есть более тонкие настройки. Стоит присмотреться, когда потребуется реализация.

.compareTo()

  • .compareTo() это метод интерфейса Comparable
  • По умолчанию класс Object не реализует этот интерфейс. Однако реализация есть у подклассов, например String, Integer, LocalDate и т.д.
  • Реализуя compareTo в классе, мы задаем natural order (естественный порядок) для экземпляров этого класса. Например, у чисел 1, 2, 3 порядок очевиден, а у объектов - нет. Поэтому чтобы было понятно как сравнивать объекты, мы должны реализовать compareTo.
  • Сравнение используется в коллекциях на основе дерева, TreeSet, TreeMap например.
  • compareTo желательно согласовать с equals. Если equals говорит, что объекты равны, то compareTo должен возвращать 0.
  • compareTo обычно редко реализуют. В случаях, когда надо сравнивать элементы, у которых по своей природе нет естественного порядка, обычно используют объект типа Comparator<T>

Массивы

Массив - это объект

  • Массив - это объект, он наследуется от Object
    • Поэтому массивы создаются через new
    • Поэтому у массива есть методы equals(), toString(), hashCode()
  • У всех видов массивов (int[], String[] и т.д.) есть скрытые классы, наследники Object
    • У самопальных массивов, вроде Person[] тоже будет скрытый класс, наследник Object, который JVM сгенерирует налету

“Проблема Arrays.asList”

Вот код:

int[] numbers = new int[] { 5, 7, 4, 21, 100 };
List<int[]> list = Arrays.asList(numbers);

Меня бесило то, что я передаю массив и получаю List<int[]>, т.е. “список массивов” вместо массива чисел. Я не понимал, как так. Да и сейчас не понимаю механику особо. Вот описание метода <T> asList(T... a). Он принимает несколько аргументов. По сути то же самое что <T> asList(T[] a). Здесь дженерики, а они по определению не работают с примитивами. Если передать массив объектов:

Integer[] numbers = new Integer[] { 5, 7, 4, 21, 100 };
List<Integer> list = Arrays.asList(numbers);

Тогда получается список этих объектов. А если передать массив примитивов, то тип элемента вычисляется как “Массив-объект”.

Обертки, boxing

Примитивы и их обертки

Категория Тип Обертка
Числа

Остальные

Зачем нужны обертки

  • Находятся в java.lang
  • Хранят разные статические утилитарные методы для своего примитивного типа
  • Используются в дженериках

autoboxing и unboxing

  • autoboxing - это упаковка примитива в его обертку
  • unboxing - это извлечение примитива из обертки
  • и то, и другое происходит во время компиляции, в соответствующих местах компилятор автоматически добавляет нужные преобразования
    • По сути это срабатывает когда примитив присваивается туда где нужен объект, и когда объект присваивается туда где нужен примитив
// autoboxing  int -> Integer
Integer x = 10;
List<Integer> numbers = List.of(10, 20, 30);

// unboxing  Integer -> int
int y = x;
int num = numbers.get(0);
  • Б  А - это синтаксический сахар над
Integer.valueOf(10);
int y = x.intValue();
// и прочими подобными конструкциями

Обертки, боксинг и коллекции

  • Коллекции появились раньше дженериков
  • В них все хранилось в виде Object
  • За счет оберток и боксинга можно было делать например вот так:
coll.add("Hello");
coll.add(person);
coll.add(5);  // <-- 5 боксится в Integer
  • Правда при извлечении приводить к нужному типу в таком случае приходилось бы явно, т.к. все хранится как Object и компилятор не знает, чего мы понадобавляли.

Дженерики

Стирание типов

  • type erasure (“стирание” типов) - это базовый механизм работы дженериков
  • после компиляции никаких дженериков не существует, они как бы “стираются”
  • стирание - это механизм замены типа дженерика на реальный тип
    • на какой именно? по верхней доступной границе

Код с дженериками:

// классы для примеров
class Animal { }
class Tiger extends Animal { }
class Box<T> {  // <-- Вводим дженерик-тип T
    private T value;  // <-- И используем его в классе вместо "реального" типа тут

    public void set(T value) {  // <-- и тут
        this.value = value;
    }

    public T get() {  // <-- и тут
        return value;
    }
}

var box = new Box<Tiger>();  // <-- Закрываем дженерик конкретным типом
Tiger tiger = box.get();  // <-- Руками ничего приводить не приходится

После компиляции код с дженериками превращается в обычный код без дженериков. В нужных местах компилятор просто расставляет приведение к нужным типам:

class Box {  // <-- Никакого T после компиляции нет.
    // У T в объявлении не было ограничений, поэтому он 
    private Object value;  // заменился по верхней границе (на Object, а не на Animal).

    public void set(Object value) {  // <-- Везде, где был T,
        this.value = value;
    }

    public Object get() {  // <-- произошла замена на реальный тип, Object в данном случае
        return value;
    }
}

Box box = new Box();  // <-- Никаких дженериков нет
Tiger tiger = (Tiger) box.get();  // <-- Компилятор подставил приведение к нужному типу

Если дженерик ограничен:

class Box<T extends Animal> {  // <-- Указано, что T это подтип Animal
    private T value;
    public void set(T value) {...}
    public T get() { return value; }
}

var box = new Box<Tiger>();  // <-- Желаемый тип - Tiger
Tiger tiger = box.get();
class Box {
    private Animal value;  // <-- T везде заменился
    public void set(Animal value) {...}
    public Animal get() { return value; }  // <-- по типу-ограничителю
}

Box box = new Box();  // <-- Дженериков нет
Tiger tiger = (Tiger) box.get();  // <-- Компилятор знает, что мы хотели Tiger для Box
// Tiger без проблем ложится в Animal внутри Box

Почему в дженериках нельзя использовать примитивы

  • В дженериках нельзя использовать примитивы:
List<int> numbers = List.of(10, 20, 30);  ❌
List<Integer> numbers = List.of(10, 20, 30);  ✅
  • Это из-за стирания типов. Механика стирания типов работает только с объектами, а не с примитивами. Вместо int-дженерика в качестве реального типа невозможно поставить Object, потому что int не является наследником Object. Следовательно, чтобы стирание работало, нужен объектный тип, поэтому используется Integer.

Бины (beans)

Что такое бины

  • ❓ Что такое бины и что они собой представляют?
  • ❓ Кто управляет жизненным циклом бинов?
  • Бины - это основные “строительные блоки” в Spring-программах
  • Бины представляют собой объекты, жизненный цикл которых находится в руках контейнера Spring IoC
    • Контейнер создает бины, снабжает зависимостями, инициализирует и уничтожает
  • TODO: Бины должны быть stateless?

Как создать бины

  • ❓ Как создать бин?
  • ❓ Можно ли получить бин?
  • Бины создаются автоматически, их создает контейнер
  • Можно явно запросить у контейнера бин
    • Но это считается в большинстве случаев антипаттерном
  • Так что в основном надо просто объявить бины с помощью аннотаций, а созданием занимается спринг

Объявление бинов

Аннотированный класс

  • Просто помечаем классы биновыми аннотациями
    • @Component - бин общего назначения, “нейтральный, просто бин”
      • Имеет несколько разновидностей
        • @Service
        • @Repository
        • @Controller  @RestController
        • прочие, “тысячи их”
  • Бин получает имя такое же как название класса (с маленькой буквы)

Конфигурационный класс

  • Комбинация: @Configuration на класс + @Bean на метод.
    • В методе создаем руками и возвращаем нужный инстанс.
  • Бин получает имя как название метода.
@Configuration  // <-- 
public class AppConfig {
    @Bean  // <-- Первый какой-нибудь бин
    public UserService userService() {
        return new UserService();
    }
  
    @Bean  // <-- Другой какой-нибудь бин
    public OrderService orderService() {
        return new OrderService();
    }
}
  • Когда этот способ хорош
    • Когда бины надо создавать из библиотечных классов, этот способ является единственным решением, поскольку “чужой” класс мы не можем аннотировать непосредственно биновыми аннотациями.
  • Особенности
    • По умолчанию в этом подходе бины создаются со скопом singleton.
      • Т.е. при каждом вызове метода возвращается один и тот же инстанс.
      • Если надо чтобы метод возвращал каждый раз новый инстанс, надо дополнительно добавить методу аннотацию @Scope("prototype")
        • Но это считается антипаттерном. Исторически @Configuration-класс используется для объявления бинов, которые должны существовать именно в единственном экземпляре на все приложение.

Жизненный цикл бинов

  • Жизненный цикл - это процесс из нескольких этапов, которые бин проходит от момента создания до момента уничтожения
  • Основные этапы такие
    • Создание бина
    • Пост-процессинг
      • Пре-инициализация (делается через BeanPostProcessor)
      • Инициализация (выполнение метода бина, аннотированного через @PostConstruct)
      • Пост-инициализация (делается через BeanPostProcessor)
    • Жизнь-работа
    • Освобождение ресурсов (выполнение метода бина, аннотированного через @PreDestroy)
    • Уничтожение бина
  • TODO: надо примеры, когда какой этап полезен.

Скоуп бинов (scope)

  • Адекватного русского устоявшегося перевода нет. “Область видимости” не отражает суть.
  • Суть скоупа это “время жизни + количество экземпляров”.
  • Скоупы делятся на категории
    • core - так сказать, скоупы обычного спринг-приложения
      • singleton - бин существует один на все приложение, контейнер при требовании такого бина создает его, кэширует, а потом каждый раз возвращает один и тот же инстанс.
      • prototype - контейнер каждый раз создает новый инстанс бина.
    • web - скоупы для спринговых веб-приложений (Spring MVC)
      • request - на каждый HTTP-запрос создается новый инстанс бина.
      • session
      • application
      • websocket
      • TODO: примеры, какие бины имеют такие скоупы
    • прочие - в других типах спринг-проектов могут быть свои скоупы
  • Специализированные скоупы дополняют базовые, т.е. в веб-приложениях доступны core-скоупы + собственные веб-скоупы
  • Скоуп бину можно задать явно через аннотацию @Scope("тип-скоупа") (вешается на класс бина).

Пост-процессинг бинов через BeanPostProcessor

@Component  // Класс, реализущий BeanPostProcessor, надо зарегистрировать как бин
public class SimpleBeanPostProcessor implements BeanPostProcessor {

    @Override  // Модифицируем бин до вызова @PostConstruct
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        System.out.println("Before @PostConstruct: " + beanName);

        // Как процессор понимает, что должен обработать пришедший бин, варианты:
        if (bean instanceof Auditable) {  // По типу
            // Изменяем бин как хотим
        }  
        if ("dataSource".equals(beanName)) {  // По имени бина
            // Изменяем бин как хотим
        }  
        if (bean.getClass().isAnnotationPresent(MyCustomAnnotation.class)) {  // По аннотации
            // Изменяем бин как хотим
        }  
        
        return bean;
    }

    @Override  // Модифицируем бин после вызова @PostConstruct
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        System.out.println("After @PostConstruct: " + beanName);

        // Снова делаем проверку, надо ли обрабатывать бин
        
        // здесь часто создаются прокси (AOP)
        return bean;
    }
}
  • BeanPostProcessor это интерфейс.
  • Интерфейс довольно старый, но почти не менялся за 20 лет, относится к самой базе.
    • Нужен чтобы обрабатывать бины после их создания.
      • Например, вызвать методы инициализации, заменить бин на прокси.
  • Чтобы спринг увидел реализацию, надо этот класс зарегистрировать как бин.
    • Не обязательно аннотацией, можно любым способом, просто аннотацией удобно.
  • У интерфейса два метода
    • postProcessBeforeInitialization - выполняется перед @PostConstruct
    • postProcessAfterInitialization - выполняется после @PostConstruct
    • каждый из этих методов возвращает объект
      • можно вернуть оригинальный бин, который пришел в метод
        • например, положить ему в значения полей свойства из properties-файла (примерно так и работает @Value например)
      • а можно вернуть другой объект (так например создаются прокси)
  • “before”-метод используется реже “after”-метода
    • да и в целом оба метода обычно используются разработчиками библиотек, нежели прикладными программистами
    • От @PostConstruct отличается тем, что @PostConstruct - это работа с одним конкретным бином и там по сути возможности ограничены только какой-то настройкой бина. А BeanPostProcessor срабатывает на все бины и позволяет по сути заменить бин другим объектом.
  • Можно создавать много реализаций BeanPostProcessor.
    • Здесь принцип “1 процессор - на 1 вид обработки (сквозной задачи)”. Например, один процессор добавляет логирование, а другой - транзакционность. Нет смысла делать все в одном процессоре, будет не SOLID.
    • Если процессор предназначен для конкретных бинов, внутри методов можно проверять это (по типу, по имени бина, по наличию аннотаций на нем).
  • Каждый бин проходит через все процессоры.
    • TODO: Процессоры можно организовать в нужном порядке. Если не организовывать, то порядок будет произвольный.

Проблемы с бинами

Несколько бинов одного типа

Суть проблемы

@Component
class EmailService implements NotificationService {}

@Component
class SmsService implements NotificationService {}
@Autowired  // <-- Что внедрять? EmailService или SmsService?
private NotificationService service;
  • Спринг не поймет, какой бин внедрять - EmailService или SmsService
  • Надо явно ему подсказать, что выбрать

@Qualifier

@Autowired
@Qualifier("emailService")
private NotificationService emailService;

@Autowired
@Qualifier("smsService")
private NotificationService smsService;
  • @Qualifier это способ явно указать имя бина, который мы хотим внедрить
  • Этот способ подходит только для явного жесткого указания, какой бин нужен
    • Нельзя, например, считать из properties имя нужного бина и передать в @Qualifier, это архитектурно не поддерживается в спринге

@Profile

@Service
@Profile("prod")
public class ProdDataSource implements DataSource {}

@Service
@Profile("dev")
public class DevDataSource implements DataSource {}
  • @Profile это дополнительный способ организации вариативности бинов
    • Для разных окружений, например prod, dev
  • По профилю спринг определяет, создавать бин или нет. В примере выше у нас две версии бина. Но одна для прода, другая - для дева.
    • Спринг автоматически выберет нужный в зависимости от того, какое окружение мы укажем в настройках
      • Есть два варианта задать окружение
        • Через properties spring.profiles.active=dev
        • Через переменную окружения SPRING_PROFILES_ACTIVE=dev
  • @Profile и @Qualifier можно использовать вместе
    • @Profile определяет создавать  не создавать, а @Qualifier определяет, какой именно из созданных бинов внедрять

Spring IoC

  • IoC - Inversion of Control, принцип согласно которому задачу создания объектов мы делегируем какой-то абстракции
    • Т.е. не сами создаем объекты (через new например), а их за нас создает какой-то специальный инструмент
  • В Spring эту задачу выполняет ApplicationContext
    • Он ищет классы, аннотированные биновыми аннотациями, регистрирует их у себя и когда где-то требуется бин, он его создает и внедряет

Dependency Injection

Способы внедрения зависимостей, @Autowired

  • В спринге три способа внедрения зависимостей
    • Через конструктор
    • Через сеттеры
    • Через поле
  • Все они используют аннотацию @Autowired для маркировки, что требуется автоматическое внедрение зависимости.
    • Аннотация вешается на соответствующий член класса - конструктор, метод-сеттер или на поле.
    • Сама по себе она ничего не внедряет, а просто спринг использует ее на разных этапах создания бина для понимания, как внедрять зависимости.
      • Если @Autowired на конструкторе, то зависимости внедряются на этапе создания бина.
      • Если @Autowired на методе или поле, то внедрение происходит на этапе пост-процессинга бина.
  • Предпочтительным считается внедрение через конструктор
    • Потому что зависимость после внедрения нельзя перезаписать, следовательно не сломаешь поведение.
    • Зависимости через конструктор обязательные, стало быть явно видно что нужно классу для работы.
    • Зависимости проще замокать в тестах.

Конструктор

@Component
public class UserService {
    private final OrderService orderService;

    @Autowired // Вешаем @Autowired на конструктор
    public UserService(OrderService orderService) {
        this.orderService = orderService;
    }
}
  • Если конструктор один, то @Autowired можно не вешать.
  • Если конструкторов несколько, тогда один из них явно надо пометить @Autowired, иначе будет ошибка.

Сеттеры

@Component
public class UserService {
    private OrderService orderService;

    @Autowired  // Вешаем @Autowired на метод
    public void setOrderService(OrderService orderService) {
        this.orderService = orderService;
    }
}

Поле

@Component
public class UserService {
    @Autowired  // Вешаем @Autowired на поле
    private OrderService orderService;
}

Прокси

Зачем нужны прокси

  • Концептуально под прокси понимается обертка над исходным объектом
    • Клиент работает с оберткой, при этом обертка выглядит для него как оригинальный объект, т.е. имеет все те же методы
  • Прокси позволяют дополнить методы оригинального объекта дополнительными действиями (“обвязка”), без модификации кода оригинальных методов
    • Как правило это что-то инфраструктурное, вроде логирования, транзакционности, метрики  профилирование и т.д.
      • Например, перед вызовом оригинального метода запустить таймер, потом вызвать метод, а потом залогировать значение таймера, чтобы понять как долго выполнялся метод - это хороший пример применения прокси
    • Действия для всех методов обычно одинаковые
      • Обычно вопрос в том, к каким методам их применять, а к каким нет, а не “для метода foo действия A и B, а для метода bar - действия Z, X”
    • Итого - прокси имеет все такие же методы как оригинальный объект и при вызове этих методов срабатывает обвязка + выполняется метод оригинального объекта
  • Через прокси реализуется аспектно-ориентированное программирование (AOP)

Как технически создаются прокси

Примерно реализация выглядит так:

@Component
public class ProxyBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        if (!(bean instanceof Foobar)) return bean;

        return Proxy.newProxyInstance(
            bean.getClass().getClassLoader(),
            bean.getClass().getInterfaces(),
            (proxy, method, args) -> {

                // 1. если есть аннотация → логируем
                if (method.isAnnotationPresent(Loggable.class)) {
                    System.out.println("LOG before " + method.getName());
                    Object result = method.invoke(bean, args);
                    System.out.println("LOG after " + method.getName());
                    return result;
                }

                // 2. если метод bar → вообще запрещаем
                if (method.getName().equals("bar")) {
                    throw new RuntimeException("bar is forbidden");
                }

                // 3. иначе — просто вызываем
                return method.invoke(bean, args);
            }
        );
    }
}
  • Proxy.newProxyInstance - для нашего удобства (механизм Java), чтобы спринг сам создал обертку для оригинального класса, а нам через лямбду осталось только осталось написать обвязку для методов.
    • Через лямбду мы реализуем желаемую обвязку. Спринг нам дает оригинальный метод, переданные ему аргументы. Поэтому мы можем выполнить обвязку и в любой момент вызвать оригинальный метод.
    • Когда на проксе вызывается любой метод, то выполняется эта лямбда.
    • Обычно прокси возвращают из “after”-метода процессора, потому что к этому моменту бин уже прошел инициализацию и готов к работе.

AOP (Aspect-Oriented Programming)

Парадигма AOP

  • AOP - это парадигма программирования
    • Код обычно делится на бизнес-логику и сквозную логику, т.е. дополнительную, инфраструктурную (метрики, логирование, транзации, обработка исключений и т.д.)
    • AOP парадигма подразумевает выделение такой сквозной логики в отдельные классы  модули, которые называют аспектами
    • Т.о. аспекты реализуется отдельно от бизнес-логики, не зашумляют ее, а затем применяются к ней с помощью средств языка  фреймворка
  • В джаве AOP реализуется через прокси

aspect, advice, pointcut, join point, introduction

  • Это специфичные для джавы понятия. В других системах мб что-то похожее, но в общем именно эти формулировки - джавовские. Но вся эта история изначально пошла из джавы, поэтому остальные во многом эти идеи переняли.
  • join point - это точка кода, к которой можно присоединить сквозную логику
    • пример таких точек
      • создание объекта
      • изменение поля
      • вызов метода
    • но в спринге по сути это всегда именно вызов метода
  • pointcut - правило, которое определяет на какие join point’ы применять сквозную логику
    • реализуется через аннотацию @Pointcut в которую передается выражение вроде регулярки (язык AspectJ)
  • advice - это “совет”, в какой момент времени по отношению к join point выполнять сквозную функциональность
    • выражается несколькими аннотациями, вроде @Before, @After, @Around и т.д.
      • например, перед точкой (“перед выполнением метода”), после точки (“после выполнения метода”), “до и после (around) выполнения метода” и прочие
  • aspect - это класс, в котором реализована сквозная функциональность
    • Тут же описывается как она привязывается к join point’ам (через pointcut’ы и advice’ы)
    • каждый аспект реализуется отдельным классом, аннотированным через @Aspect
    • все остальные аннотации навешиваются на методы внутри этого класса

Пример:

@Service
class UserService {  // Бизнес-логика

    public void createUser(String name) {
        System.out.println("Creating user: " + name);
    }

    public void deleteUser(String name) {
        System.out.println("Deleting user: " + name);
    }
}

@Aspect
@Component
class LoggingAspect {  // Сквозная функциональность

    @Pointcut("execution(* UserService.*(..))")
    public void userMethods() {}

    @Before("userMethods()")
    public void before() {
        System.out.println("BEFORE");
    }

    @After("userMethods()")
    public void after() {
        System.out.println("AFTER");
    }

    @Around("userMethods()")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        System.out.println("AROUND BEFORE");
        Object result = pjp.proceed();
        System.out.println("AROUND AFTER");
        return result;
    }
}
  • P.S. Для ознакомления. Фактически пишется от руки редко, в основном AOP используется через готовые библиотечные аннотации

Как @Aspect связан с прокси

  • Спринг находит классы, помеченные через @Aspect
    • По поинткатам понимает, на какие бины должен работать аспект и когда эти бины создаются, он делает для них прокси

Транзакции

@Transactional

  • В спринге есть встроенные средства для упрощения работы с транзакциями
  • Главная аннотация @Transactional
    • Можно аннотировать через нее метод, в котором идет работа с БД
      • Если в методе происходит исключение, транзакция автоматически откатывается, иначе - автоматически коммитится
    • Работает независимо от конкретной СУБД, в своем коде опирается на отвязанные от СУБД вещи, которые для конкретных СУБД реализует PlatformTransactionManager
  • Как работает
    • Когда мы применяем @Transactional к какому-то методу  методам, то спринг создает прокси и регистрирует его в качестве бина.
    • В этих методах в проксе есть транзакционная обвязка, посреди которой вызывается метод оригинального объекта.

Проблемы с транзакциями

@Transactional и self-invocation

  • self-invocation - это когда метод класса вызывает внутри себя другой метод этого же класса
  • Суть проблемы
    • Если в каком-то “не @Transactional”-методе класса вызвать другой метод, помеченный через @Transactional, то транзакционная обвязка не сработает
  • Причина проблемы
    • Надо хорошо себе представить и разделить два объекта - проксю и оригинальный. В проксе все те же методы, что и в оригинальном объекте. Если метод не был помечен @Transactional, то в проксе в нем не будет транзакционной обвязки. Раз.
      • Далее, из этого метода прокси вызывается этот же метод на оригинальном объекте. Т.е. всё, перешли из прокси в оригинальный объект, в котором и подавно нет никаких транзакций. Два.
      • Выполнение идет уже в оригинальном объекте, поэтому когда вызываем @Transactional-метод, вызывается он на оригинальном объекте тоже, но обвязка-то находится в проксе! Три.
      • Поэтому и не срабатывает транзакция, ведь оригинальный объект никаких транзакционных обвязок не содержит.
  • Как решать проблему
    • Избежать вызов через this
      • По сути, самый ходовой способ - вынести транзакционную логику в отдельный класс, внедрить в оригинальный класс этот класс с транзакциями и работать через него

Конфигурация приложения

starter

  • starter это концепция из spring boot
  • стартер - это артефакт, содержащий список зависимостей, типично необходимых для работы с областью, для которой предназначен стартер, и конфигурацию этих зависимостей
    • например, для работы с веб-приложениями есть spring-boot-starter-web
      • в него входят спринговые библиотеки для веба, типа mvc, работы с json, а также веб сервер (spring-boot-starter-tomcat, т.е. стартер может содержать и другие стартеры) и т.д.
    • большой плюс стартера в том что версии зависимостей подобраны совместимые
  • артефакт - это понятие maven, можно сказать что это jar-файл + pom
    • т.е. артефакт - это логическая единица, а не единый файл
  • работает примерно так
    • в репозитории мавена хранится jar стартера и его pom
    • когда мы подключаем к себе в проект стартер (т.е. указываем стартер в pom своего проекта), то мавен обращается в удаленный репозиторий, читает там pom этого стартера и вытягивает нам локально все зависимости из него + скачивает jar-ник стартера тоже как еще одну зависимость
    • этот jar-ник содержит классы конфигурации для спринга, т.о. у нас оказываются все зависимости + классы, которые их конфигурируют как надо, например там могут быть объявлены бины, настройки для них и т.д.
    • в итоге, когда мы запускаем спринговое приложение, то получаем за счет этих конфигов стартера набор готовых к работе бинов

@ComponentScan

  • @ComponentScan активирует механизм поиска бинов
    • аннотация позволяет явно указать спрингу пакеты, в которых надо искать бины
    • бины будут искаться в указанных пакетах и их подпакетах
    • без этой аннотации поиска не будет
      • но следует учитывать, что @ComponentScan уже включен например в аннотацию @SpringBootApplication
  • По умолчанию в спринг-бут приложении бины ищутся так
    • Мы запускаем приложение через SpringApplication.run(тут класс-"точка входа")
    • Спринг начинает поиск бинов в том же пакете, что и этот класс, и его подпакетах - это поведение по умолчанию (как раз за счет того что @ComponentScan включен в @SpringBootApplication)
      • Обычно пакеты размещаются так, что есть один корневой, а в него все остальные вложены, соответственно поиск идет от этого корня и @ComponentScan вообще трогать не надо
      • Но если вдруг по каким-то причинам надо места поиска расширить, можно дополнительно к дефолтному месту поиска добавить и другие пакеты

@SpringBootApplication

  • @SpringBootApplication это комбинированная аннотация, содержит в себе @Configuration, @ComponentScan, @EnableAutoConfiguration
  • Соответственно, используя эту аннотацию мы сразу активируем три механизма, лежащий за этими аннотациями

Автоконфигурация

  • Автоконфигурация — это механизм Spring Boot, который анализирует classpath и настройки приложения и создаёт нужные бины, если они ещё не определены программистом
    • включается через @EnableAutoConfiguration
    • например: если есть зависимости для работы с БД и настройки подключения, Spring может автоматически создать бин DataSource
    • если программист сам объявил такой бин, автоконфигурация его не создаёт
    • удобство в том, что не нужно вручную описывать стандартные бины - достаточно подключить зависимости и задать настройки

# Модели взаимодействия

## Модель Request-Response

- Это модель взаимодействия "один к одному".
- Сервис А обращается к сервису Б и ждет от него ответ, чтобы продолжить свою работу.
- Ключевые вещи здесь:
  - Сервис А знает, к кому он обращается. И это общение строго двух сервисов.
    - ("двух" имеется ввиду, что если А послал запрос в Б, то ему на этот запрос ответит сервис Б, а не В)
  - Сервис А должен сначала получить ответ на свой запрос, прежде чем продолжить свою работу.
    - Т.е. концептуально эта модель по своей природе **синхронная**, даже если технически она выполнена асинхронно.
      - Например, gRPC технически умеет работать в синхронном режиме и в асинхронном. Отличаются они технически. Но концептуально все равно оба синхронные - gRPC должен вернуть ответ, чтобы метод выполнился до конца.
        - Синхронный режим - метод блокируется до тех пор, пока gRPC-вызов не вернет ответ.
        - Асинхронный режим - метод продолжает выполняться. gRPC-вызов возвращает нам future, через который мы можем попробовать получить результат. Если вызов успел выполниться к моменту, когда мы пытаемся взять результат, то получаем результат сразу. Если вызов не успел выполниться - тогда метод блокируется до того момента, пока вызов не завершится.
      - Есть даже Kafka RPC, там модель request-response симулируется через очереди. Технически это вообще получается pub / sub, но концептуально это все та же синхронная request-reponse модель.



## Модель Pub / Sub

- Это модель взаимодействия "один ко скольки хочешь".
- Реализуется через очередь сообщений.
- Сервис А кладет сообщение в очередь и на этом его "взаимодействие" завершается. Он не знает, кто вообще будет на это сообщение реагировать. Это может быть какой-то один сервис, а может быть сотня. "А" не ждет ни от кого ответа, потому что ни к кому по сути и не обращался.
- Другой сервис Б может прочитать это сообщение, выполнить какую-то работу и отправить в очередь свое сообщение. "А" может на него отреагировать.
- Концептуально эта модель - асинхронная.
- Ключевые вещи:
  - Прямых обращений нет. Сервисы не знают, кто реагирует на их сообщения.
  - Ожидания как такового нет. Есть реакция на появление в очереди сообщения.

## REST и gRPC

- Концептуально и то, и другое относятся к модели Request-Response, поэтому идейно они взаимозаменяемы, но есть нюанс.
  - Границы использования
    - REST - годится для как для работы внутри своей системы, так и для внешних интеграций, т.е. для связи нашей системы с "не нашими".
    - gRPC - годится только внутри своей системы из-за технических сложностей.
- Для каких операций применяется
  - Хорошо
    - Для запросов данных. Например, получить цену товара, остатки на складе, выбрать подходящие товары по фильтру.
  - Сомнительно
    - ???
- Техническое сравнение
  - gRPC дает скорость, эффективность передачи.
    - За счет чего - можно отдельно разобраться для обоснования, но пока оставлю как факт.
  - Поэтому критерий выбора прост
    - Для связи с внешним миром - REST.
    - Для связи внутри системы - если есть возможность, то gRPC. Если почему-то нету, тогда уж REST.

## Сценарий: магазин с фронтом, каталогом, заказами, складом и аналитикой

### 1. Фронтенд → бэкенд: REST

**Контекст.** Браузер и мобильное приложение грузят каталог, корзину, статус заказа. Запросов сотни тысяч в день, но каждый — «дай данные сейчас». Разработчик должен иметь возможность открыть DevTools, увидеть URL и JSON, поправить запрос.

**Почему REST.** HTTP + JSON — родной язык браузера. Кэширование на CDN (`Cache-Control`) снимает нагрузку с бэкенда. Ошибку видно глазами: `404`, `401`, тело ответа.

**Что будет с другими:**
- **gRPC** — браузер не умеет его нативно, нужен gRPC-Web и прокси на границе. Ответ — бинарный Protobuf, в DevTools не прочитать. Для публичного API это лишний слой без выгоды: узкое место здесь — сеть пользователя, а не сериализация.
- **Kafka** — это лог событий, а не request-response. Клиент не может «спросить» текущую корзину: ему пришлось бы держать постоянное соединение и самому собирать состояние из потока. Для фронта это абсурд.

**Итог:** REST здесь не «просто популярен», а единственный, кто даёт кэш, читаемость и нулевой порог входа для фронта.

---

### 2. Сервис заказов → сервис каталога: gRPC

**Контекст.** При оформлении заказа сервис заказов синхронно проверяет цену и наличие по 20–50 позициям. Это внутренний вызов, сотни раз в секунду в пике, ответ нужен немедленно, чтобы показать пользователю итог. Контракт между командами зафиксирован.

**Почему gRPC.** Protobuf даёт жёсткий контракт: если каталог поменял поле — заказы падают на компиляции, а не в проде. HTTP/2 мультиплексирует запросы — 50 позиций летят по одному соединению, а не 50 TCP-хендшейков. Размер пакета и latency ниже, чем у JSON/REST, и на таком объёме это уже деньги.

**Что будет с другими:**
- **REST** — работает, но на 50 вызовах на заказ и высоком RPS вы платите за JSON-парсинг и новые соединения. Контракт «мягкий»: опечатка в поле вылезет в рантайме.
- **Kafka** — не подходит по сути: пользователь ждёт ответа *сейчас*. Асинхронная проверка наличия означает, что заказ подтверждается до проверки — а это уже другая бизнес-модель (и другие проблемы: oversell).

**Итог:** gRPC здесь — про синхронность + контракт + скорость одновременно. REST тянет, но хуже; Kafka ломает саму модель «проверить перед подтверждением».

---

### 3. Заказ создан → склад, бонусы, email, аналитика: Kafka

**Контекст.** Заказ оформлен. Его должны обработать четыре независимых сервиса. Аналитика может лежать полчаса — заказ из-за этого падать не должен. Через месяц выяснится, что бонусы считались с багом, и нужно пересчитать за прошлый период.

**Почему Kafka.** `OrderCreated` публикуется один раз. Каждый потребитель читает в своём темпе; падение аналитики не блокирует заказ. Событие хранится (retention), оффсет можно отмотать и перечитать — пересчёт бонусов за прошлый месяц становится операцией, а не археологией.

**Что будет с другими:**
- **REST/gRPC** — сервис заказов становится оркестратором: дёргает всех четверых. Упала аналитика — либо заказ падает (плохо), либо вы глотаете ошибку и теряете событие (тоже плохо). А пересчитать бонусы задним числом нечем: данные «испарились» после ответа.
- **REST + retry-очередь** — половина Kafka, написанная руками: своя очередь, свои ретраи, свой retention, свои оффсеты. Работает, пока не понадобится несколько независимых потребителей и replay.

**Итог:** Kafka здесь решает именно то, чего REST/gRPC не умеют в принципе: веерная доставка без связности + хранение истории + повторное чтение.

## Сводка на одном сценарии

| Участок               | Способ    | Ключевая причина                | Почему не другие                                             |
| --------------------- | --------- | ------------------------------- | ------------------------------------------------------------ |
| Фронт → бэкенд        | **REST**  | кэш, читаемость, ноль порога    | gRPC — прокси и бинарь; Kafka — не request-response          |
| Заказы → каталог      | **gRPC**  | синхронно + контракт + скорость | REST — медленнее и мягкий контракт; Kafka — ломает «проверить до подтверждения» |
| Заказ → 4 потребителя | **Kafka** | веер, развязка, replay          | REST/gRPC — оркестрация, потери, нет истории                 |

Если хотите, могу углубить любой из трёх узлов — например, что конкретно ломается при переходе «заказы → каталог» с gRPC на REST под нагрузкой, или как выглядит replay в Kafka на этом же примере с бонусами.
